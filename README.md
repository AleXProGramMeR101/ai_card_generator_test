# Генератор карточек товаров для B2B-магазина КИП

Прототип с веб-интерфейсом и консольным режимом: принимает JSON с данными о приборе и с помощью LLM готовит черновик карточки товара для контент-менеджера:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- таблицу ключевых характеристик с пометкой «данных нет» для отсутствующих;
- 3–5 поисковых запросов;
- блок для менеджера: кому подходит прибор и какие задачи решает;
- список того, что нужно уточнить: недостающие характеристики, противоречия в данных.

Главный принцип: **модель не выдумывает характеристики**. Таблицу характеристик собирает код, все числа в сгенерированных текстах сверяются с входными данными, а оценочные слова без опоры на данные («надёжный», «высокая точность») отправляются на исправление.

Модель подключается через любой OpenAI-совместимый API: Groq, OpenAI, локальные Ollama, vLLM, LM Studio. Модель меняется в файле `.env`, код при этом не трогается.

## Быстрый старт (Windows)

Нужны **Python 3.10 или новее** ([python.org](https://www.python.org/downloads/), при установке отметьте «Add python.exe to PATH») и ключ API. Бесплатный ключ Groq можно получить на [console.groq.com](https://console.groq.com/keys), работает только с VPN.

```bat
git clone <ссылка на репозиторий> card-generator
cd card-generator
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
copy .env.example .env
```

Откройте файл `.env` (например, `notepad .env`), укажите адрес API в `LLM_BASE_URL` (для Groq - `https://api.groq.com/openai/v1`) и замените `your_api_key_here` на свой ключ. Затем запустите веб-интерфейс:

```bat
.venv\Scripts\python server.py
```

и откройте в браузере **http://127.0.0.1:8000**. Перетащите JSON-файл в окно загрузки или нажмите на один из трёх примеров.

Консольный режим без браузера:

```bat
.venv\Scripts\python main.py examples\input
```

Готовые карточки появятся в папке `output`: для каждого товара файл `.json` и файл `.md`.

> Окружение не нужно активировать: команды вызывают Python из `.venv` напрямую. Так всё работает одинаково в cmd и PowerShell, без настройки политики выполнения скриптов.

<details>
<summary>Linux / macOS</summary>

```bash
git clone <ссылка на репозиторий> card-generator && cd card-generator
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

## Веб-интерфейс

Одна страница:

- **окно загрузки**: перетащите файл или нажмите и выберите. Принимаются только файлы `.json` до 50 МБ: другие форматы отклоняются и в браузере, и на сервере. В файле может быть до 10 товаров;
- **три примера**: «Пример из ТЗ» (DM 02, минимум данных), «МП4-У с сайта» (грязные и противоречивые данные), «МП3-У, полные данные». Ссылка «JSON» рядом с примером открывает исходный файл;
- **результат разбора**: какие товары найдены в файле, какие отклонены и почему. Карточки генерируются по одной, готовые появляются сразу; между товарами можно переключаться;
- **карточка**: SEO-заголовок и описание со счётчиками символов и кнопками «Копировать», поисковые запросы, таблица характеристик с источником каждого значения, блок для менеджера и список «Требует уточнения»;
- **скачать**: JSON или Markdown по текущему товару; если товаров несколько - все карточки одним JSON.

Под страницей - HTTP API, его можно вызывать и напрямую. Описание с примерами - на странице `/docs`.

| Метод | Адрес | Что делает |
|---|---|---|
| `POST` | `/api/upload` | принимает `.json` (multipart, поле `file`) и проверяет товары |
| `POST` | `/api/generate` | принимает один товар (JSON в теле) и возвращает карточку и её Markdown-версию |
| `GET` | `/api/examples` | список примеров |
| `GET` | `/api/examples/{id}` | разобранный пример |

Чтобы демонстрационный стенд не израсходовал лимиты ключа, с одного адреса разрешено не больше 20 генераций в минуту (`WEB_RATE_LIMIT_PER_MINUTE`).

### Запуск на сервере

Самый простой вариант, без HTTPS:

```bash
.venv/bin/python server.py --host 0.0.0.0 --port 8000
```

Страница будет доступна по адресу `http://<IP-сервера>:8000` или `http://<IP-сервера>.nip.io:8000`: сервис [nip.io](https://nip.io) превращает IP в доменное имя без регистрации.

С HTTPS через [Caddy](https://caddyserver.com) (сертификат он получит сам, нужны открытые порты 80 и 443):

```bash
nohup .venv/bin/python server.py > server.log 2>&1 &
caddy reverse-proxy --from 203-0-113-10.nip.io --to 127.0.0.1:8000
```

Вместо `203-0-113-10` подставьте IP сервера через дефисы. Если сертификат для nip.io не выдался из-за лимитов Let's Encrypt, используйте аналогичный сервис `sslip.io`.

## Входные данные

Файл содержит один товар или список товаров:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

| Поле | Обязательное | Комментарий |
|---|---|---|
| `name` | да | Название товара |
| `manufacturer` | нет | Производитель |
| `category` | нет | Подсказка для определения категории |
| `specs` | нет | Объект «характеристика → значение». Числа и списки приводятся к строкам |
| `description` | нет | Текст описания или фрагмент паспорта |

Как обрабатываются ошибки:

- **битый JSON** - сообщение с номером строки и столбца, остальные файлы обрабатываются дальше;
- **пустое или отсутствующее `name`, `specs` не в виде объекта** - понятное сообщение по конкретному товару, остальные товары из файла обрабатываются;
- **пустые строки и `null`** считаются отсутствующими данными: в карточке «данных нет», в отчёте пункт «передана без значения»;
- **кроме названия, ничего нет** - модель не вызывается, сервис сообщает, какие данные добавить;
- **лишние поля** (`sku`, `price` и т. п.) не мешают и сохраняются в результате;
- файлы читаются в UTF-8 (в том числе с BOM из «Блокнота») и в Windows-1251.

## Результат

`output/<название>.md` - карточка для копирования: заголовок и описание со счётчиками символов, таблица характеристик с источником каждого значения, запросы, блок для менеджера и раздел **«Требует уточнения»**.

`output/<название>.json` - то же в структурированном виде:

```json
{
  "input": { "...": "исходные данные без изменений" },
  "card": {
    "seo_title": "...", "seo_title_length": 62,
    "seo_description": "...", "seo_description_length": 1034,
    "key_specs": [
      {"name": "Диаметр корпуса", "value": "160 мм", "source": "specs"},
      {"name": "Измеряемая среда", "value": "жидкости, пар и газ", "source": "description"},
      {"name": "Диапазон измерений", "value": "данных нет", "source": "none"}
    ],
    "search_queries": ["..."],
    "manager_note": {"suitable_for": ["..."], "solves": ["..."]}
  },
  "quality": {
    "status": "needs_review",
    "category": "манометр",
    "schema_source": "config",
    "completeness": 0.92,
    "missing_fields": [{"name": "Диапазон измерений", "critical": true}],
    "needs_clarification": ["..."],
    "warnings": [],
    "dropped_specs": [],
    "attempts": 1,
    "model": "openai/gpt-oss-120b"
  }
}
```

`source` показывает, откуда взято значение: `specs` - из характеристик, `description` - найдено моделью в описании и подтверждено цитатой, `none` - данных нет.

`status` равен `ok`, если важные характеристики заполнены из блока характеристик, все проверки пройдены и уточнять нечего. Иначе `needs_review`: например, если важная характеристика найдена только в описании, входной текст оборван, в данных есть противоречия или список характеристик предложен моделью.

## Подключение другой модели

Все настройки в `.env`. Примеры:

| Провайдер | `LLM_BASE_URL` | `LLM_MODEL` | Примечание |
|---|---|---|---|
| Groq | `https://api.groq.com/openai/v1` | `openai/gpt-oss-120b` | по умолчанию |
| OpenAI | `https://api.openai.com/v1` | например, `gpt-4o-mini` | `LLM_REASONING_EFFORT=` пусто |
| Ollama (локально) | `http://localhost:11434/v1` | название из `ollama list` | `LLM_API_KEY` можно оставить пустым |
| vLLM (свой сервер) | `http://<сервер>:8000/v1` | название загруженной модели | |
| LM Studio | `http://localhost:1234/v1` | название модели | |

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `LLM_API_KEY` | - | ключ API, для локальных моделей можно оставить пустым |
| `LLM_REASONING_EFFORT` | пусто | `low` / `medium` / `high` для reasoning-моделей (gpt-oss); для остальных оставьте пустым |
| `LLM_JSON_MODE` | `true` | режим «ответ строго JSON»; если модель его не поддерживает - `false`, ответ всё равно разбирается |
| `LLM_TEMPERATURE` | `0.4` | разброс формулировок |
| `LLM_MAX_TOKENS` | `4000` | лимит ответа; `0` - не передавать (нужно для OpenAI reasoning-моделей) |
| `LLM_TIMEOUT` | `90` | таймаут запроса, секунды |
| `LLM_MAX_RETRIES` | `3` | повторы при сетевых ошибках и лимитах провайдера (429, 5xx) |
| `REPAIR_ATTEMPTS` | `1` | сколько раз просить модель исправить ответ, не прошедший проверки |
| `MAX_PRODUCT_CHARS` | `20000` | предельный объём текста одного товара; больше - товар отклоняется до запроса к модели |
| `WEB_HOST`, `WEB_PORT` | `127.0.0.1`, `8000` | адрес и порт веб-интерфейса (то же задают `--host` и `--port`) |
| `WEB_MAX_UPLOAD_MB` | `50` | предельный размер загружаемого файла |
| `WEB_MAX_PRODUCTS` | `10` | сколько товаров обрабатывается из одного файла |
| `WEB_RATE_LIMIT_PER_MINUTE` | `20` | генераций в минуту с одного адреса; `0` - без ограничения |

### Частые ошибки

| Сообщение | Причина |
|---|---|
| `Провайдер не принял ключ` (401) | неверный `LLM_API_KEY` |
| `Доступ запрещён провайдером (403)` | ключ в порядке, но провайдер блокирует ваш регион (например, Groq и OpenAI - запросы из России). Запускайте через VPN или сервер за рубежом, либо выберите провайдера, доступного из вашей страны, или локальную модель |
| `Не найдены модель или адрес API` (404) | опечатка в `LLM_MODEL` или `LLM_BASE_URL` |
| `Превышен лимит` (429) | исчерпан лимит запросов или токенов в минуту, подождите |

Если VPN-клиент даёт локальный прокси, достаточно задать его перед запуском: в PowerShell `$env:HTTPS_PROXY="http://127.0.0.1:<порт>"`.

## Как это работает

1. **Проверка входа** (код). JSON, обязательные поля, пустые значения.
2. **Определение категории** (код). По ключевым словам в названии и `category` выбирается схема из папки `schemas/`. В схеме перечислены ожидаемые характеристики, их синонимы («Резьба присоединительного штуцера» = «резьба присоединения») и пометка важности.
3. **Сопоставление характеристик** (код). Значения из `specs` раскладываются по полям схемы. Модели передаётся, какие ожидаемые характеристики уже есть, а какие нужно поискать в описании.
4. **Один запрос к модели.** Ответ - строгий JSON: тексты карточки, характеристики из описания (каждая с дословной цитатой), замеченные противоречия.
5. **Проверка ответа** (код):
   - каждое число в заголовке, описании, запросах и блоке для менеджера должно встречаться во входных данных («1,5» и «1.5» считаются одним числом);
   - цитата каждой характеристики из описания должна дословно найтись во входных данных, а числа значения - в цитате;
   - в заголовке, описании и блоке для менеджера нет оценочных слов («прочный», «надёжный», «высокая точность», «компактный», «эффективный», «стабильный» и т. п.), если их нет во входных данных;
   - в текстах для покупателя нет служебных фраз о входных данных («в описании не указано», «данных нет», «свяжитесь с представителем производителя»);
   - длина заголовка и описания, число и уникальность запросов.
6. **Исправление.** Если проверки не пройдены, модель получает конкретный список ошибок («seo_description - 640 символов: добавь примерно 260 символов (около 30 слов)», «числа 16 отсутствуют во входных данных») и возвращает исправленный JSON. Если и после этого есть проблемы, карточка всё равно сохраняется, но со статусом `needs_review` и списком проблем: проблема не скрывается.
7. **Сборка карточки** (код). Таблица характеристик в порядке схемы: значение из `specs`, иначе подтверждённое значение из описания, иначе «данных нет». Затем остальные характеристики из входа.
8. **Что уточнить** (код и модель). Код отмечает пустые значения, оборванное многоточием описание, незакрытые скобки и важные характеристики, взятые не из `specs`, а из описания: модель может неверно понять текст (например, принять условие опции «для приборов с диапазоном от N» за диапазон прибора), поэтому такое значение всегда показывается с цитатой на проверку. Модель добавляет замеченные противоречия.

### Товары без схемы

Если категория не нашлась (например, паяльник), модель в том же запросе предлагает 3–8 характеристик, по которым выбирают такой товар и которых нет во входных данных: только названия, без значений. Предложения, повторяющие имеющиеся характеристики другими словами («Рабочий диапазон влажности» при наличии «Диапазон измерения влажности»), код отбрасывает. Таблица строится из имеющихся характеристик и предложенных, в отчёте стоит `schema_source: llm_suggested`, а карточка всегда получает статус `needs_review`: список характеристик придумала модель, и человек должен его проверить. Предложенная схема сохраняется в `schemas/suggested/`. После проверки человеком её достаточно перенести в `schemas/`, и следующие товары этой категории будут проверяться по ней строго. Так каталог типизируется постепенно.

Новая категория добавляется YAML-файлом по образцу `schemas/manometer.yaml`, без изменений кода.

## Промпты и принятые решения

Промпты лежат в `card_generator/prompts.py`: системный (роль, правила, формат JSON, требования к каждому полю), пользовательский (данные товара и список ожидаемых характеристик) и промпт исправления.

- **Факты отделены от текста.** Таблицу характеристик собирает код из входных данных, модель её не переписывает. Модели доверены только тексты и поиск значений в описании, причём каждое найденное значение подтверждается цитатой, которую проверяет код. Запрет выдумывать есть и в промпте, но надёжность обеспечивает проверка, а не просьба.
- **Проверка чисел.** Выдуманные характеристики почти всегда числовые (диапазоны, давления, температуры, размеры), поэтому любое число, которого нет во входе, считается ошибкой.
- **Проверка оценочных слов.** Когда данных мало, модель добирает объём «водой» с непроверяемыми утверждениями («прочный корпус», «легко интегрируется»). Список таких оценок проверяется кодом, а промпт предлагает честную альтернативу: абзац о том, что покупателю указать или уточнить при заказе.
- **Тексты для покупателя без «кухни».** Когда данных мало, модель норовит написать прямо в SEO-описании «в описании не указано…» или отправить к производителю. Такие фразы ловит код, а промпт запрещает упоминать входные данные.
- **Важные значения из описания - только с проверкой человека.** Цитата подтверждает, что текст во входе есть, но не то, что модель поняла его правильно. Поэтому важная характеристика, найденная в описании, а не в `specs`, всегда попадает в «Требует уточнения» вместе с цитатой.
- **Один запрос вместо цепочки.** Всё генерируется одним запросом, исправление - только при ошибках. Это дешевле и укладывается в бесплатные лимиты Groq (8 тыс. токенов в минуту для `gpt-oss-120b`). По той же причине `LLM_REASONING_EFFORT=low`.
- **Модели плохо считают символы.** Поэтому длина описания задаётся в промпте ещё и через структуру (число абзацев и предложений) и в словах, а проверяет её код. Слишком длинное описание код сам обрезает по границе предложения (слишком длинный заголовок - по последней запятой), без нового запроса к модели: удаление целых предложений не может добавить в текст неверных фактов. Короткий текст код дописать не может, поэтому тут модель получает подсказку, сколько символов и слов добавить.
- **Мало данных - без генерации.** Если, кроме названия, ничего нет, модель не вызывается: 800 символов из одного названия получились бы выдумкой.
- **Заголовок без «купить» и названия магазина.** Суффикс вроде «купить в СОЮЗ-ПРИБОР» обычно добавляет шаблон сайта. Модель подбирает в заголовок 1–2 отличительных параметра (диаметр, класс точности), по которым ищут прибор.
- **Поисковые запросы - гипотезы.** Без данных Вордстата нельзя знать, какие запросы приносят продажи, поэтому промпт требует конкретные низкочастотные запросы (модель, тип и параметр) и запрещает общие вроде «манометры».
- **Блок для менеджера - тоже только из данных.** «Кому подходит» выводится из того, что есть во входе (кислород, ацетилен, атомное исполнение), а опции из описания предлагаются как допродажа.
- **Без LangChain и подобных фреймворков.** Для одного запроса с проверками они добавили бы зависимость, но не пользу. Клиент - официальный `openai` SDK, работающий с любым совместимым API.

## Ограничения и что можно улучшить

- **Неверно понятый факт может попасть в тексты.** Если модель приняла условие опции за характеристику (см. «Разбор примеров», МП4-У), значение в таблице помечается на проверку, но тот же факт может оказаться в описании и запросах: число есть во входных данных, и проверка чисел его пропускает. Улучшение: второй проход «модель-судья» или запрет использовать в текстах значения, которые пришли не из `specs`.
- **Нечисловые выдумки** ловятся только частично: оценочные слова из списка проверяет код, а утверждения вроде «подходит для пищевой промышленности» сдерживает лишь промпт. Улучшение: второй проход «модель-судья», которая сверяет каждое утверждение текста с входными данными.
- **Описание 800–1200 символов при скудных данных** (как у примера DM 02) получается менее содержательным: часть объёма занимает абзац «что уточнить при заказе». Разумно разрешать более короткое описание, когда данных мало.
- **Противоречия во входных данных** находит модель, гарантии нет. Код ловит только формальные признаки (оборванный текст, незакрытые скобки). Улучшение: сравнение значений из `specs` и описания кодом после нормализации единиц.
- **Поиск дублей среди предложенных характеристик** работает по совпадению основ слов. Это грубая эвристика: синонимы без общих слов («Масса» и «Вес») она не распознает.
- **Одна схема категории** (манометр), остальное через предложенные моделью схемы. Улучшение: схемы для всех категорий каталога, нормализация значений и единиц (МПа / кгс/см², «1.0» и «1»), на их основе - фильтры каталога.
- **Нет частотности запросов.** Улучшение: проверять предложенные запросы через API Вордстата.
- **Лимиты бесплатного Groq** (30 запросов и 8 тыс. токенов в минуту). На большой пакет SDK будет ждать и повторять запросы после 429. Для всего каталога нужен локальный vLLM или платный тариф и асинхронная пакетная обработка с ограничением скорости.
- **Веб-интерфейс без авторизации.** Для демонстрации достаточно ограничения частоты запросов; для постоянной работы - пароль на прокси (например, `basic_auth` в Caddy) или вход через корпоративную учётную запись.
- **Нет выгрузки в формат импорта 1С-Битрикс.** Следующий шаг - выгрузка в формате импорта каталога Битрикса (CSV/XML) со свойствами инфоблока из схемы категории.

## Примеры

- `examples/input/` - четыре товара:
  - `dm-02.json` - пример из задания: минимум данных, описание оборвано;
  - `mp4-u.json` - манометр МП4-У с сайта souz-pribor.ru как есть: данных много, но они грязные. Нет диапазона измерений, скобка в классе точности оборвана, параметры демпфера в описании и в таблице не совпадают (100/60 и 160/100 кгс/см²);
  - `mp3-u.json` - манометр МП3-У с того же сайта, приведённый в порядок: характеристики из таблицы, диапазоны измерений из карты заказа, измеряемая среда, описание без обрывов и противоречий. Так выглядят данные, из которых получается карточка без замечаний;
  - `vit-2.json` - гигрометр ВИТ-2 с того же сайта: категории нет в схемах, описание короткое (сокращено вручную), в поле производителя указана страна.
- `examples/bad_input/` - битый JSON, пустое название, `specs` в виде списка, товар без данных.
- `examples/output/` - результаты реального прогона:

```bat
.venv\Scripts\python main.py examples\input -o examples\output
.venv\Scripts\python main.py examples\bad_input
```

### Разбор примеров

Что показали прогоны на `openai/gpt-oss-120b` (Groq) и как на это реагирует сервис:

- **DM 02 (из ТЗ).** Данных четыре строки, описание оборвано на «...». На первой попытке модель «добрала» объём описания оценками без опоры на данные («прочный корпус», «легко интегрируется», «высокая точность») - проверка оценочных слов отправила ответ на исправление. После этого модель начала писать прямо в SEO-тексте «В описании указано только назначение прибора…» и советовать связаться с представителем производителя - такие фразы теперь ловит проверка служебных фраз. В карточке 8 характеристик «данных нет», статус «требует проверки», обрыв описания отмечен.
- **МП4-У (с сайта как есть).** Диапазона измерений в данных нет. Модель стабильно принимает за диапазон условие опции «с демпфером поставляются приборы с диапазоном показаний со 160 кгс/см²». Цитата во входе есть, поэтому проверка цитат её пропускает, но важная характеристика, взятая из описания, всегда уходит на проверку человеку вместе с цитатой - и ошибка сразу видна в «Требует уточнения». Незакрытая скобка в описании тоже отмечена. Это главный пример того, зачем нужен контроль кодом поверх промпта.
- **ВИТ-2 (категории нет в схемах).** Модель предлагала характеристики, которые уже есть под другими названиями («Рабочий диапазон влажности» при наличии «Диапазон измерения влажности»), - дубли отбрасываются кодом. Иногда предлагает неприменимое («Тип питания» у механического прибора), поэтому карточка без схемы всегда получает статус «требует проверки», а схема сохраняется на проверку в `schemas/suggested/`.
- **МП3-У (полные данные).** Пример данных, из которых должна получаться карточка без замечаний: все важные характеристики есть в блоке характеристик, противоречий и обрывов нет.

## Тесты

```bat
.venv\Scripts\python -m pytest
```

Тестам не нужны сеть и ключ API: модель подменена. Покрыты чтение входа и кодировки, схемы и синонимы, проверка чисел, цитат, оценочных слов и служебных фраз, проверки качества входа, товары без схемы, цикл исправления, ошибки провайдера, подгонка длины текстов, сохранение в JSON и Markdown, веб-интерфейс: загрузка, ограничения размера и формата, примеры, генерация, ограничение частоты.

## Логи

`logs/app.log`: подробный лог (уровень DEBUG), включая сырые ответы модели и найденные проблемы. Ротация по 100 МБ, хранятся три последних файла. В консоль выводится уровень INFO.
